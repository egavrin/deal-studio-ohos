From Prompt to ArkUI

Someone describes an app in plain words; a minute later it runs on the phone and can reach the platform. Nearly all of it happens on the device.

Where each part runs

Cloud

  • DeepSeek — writes the program source. Nothing else.

Phone

  • assembles the system prompt
  • compiles source to bytecode
  • retries on diagnostics
  • runs the machine, renders ArkUI
  • calls the platform, delivers answers

Generation

What a catalogue is

A table of what a generated program may use — one row per component, intent and calendar field. Three consumers read the same row, so they cannot drift apart.

Runtime

Why there are three trees

ArkUI redraws when a node is mutated, not when it is replaced. The machine replaces: it builds a whole new tree every frame. So the renderer keeps a third tree that persists, and copies each frame into it field by field.

Who calls whom

The usual model — build a tree, hand it to a renderer — is the wrong way round here. We never call ArkUI. We write into data it is subscribed to, and it calls us.

Four boundaries everything rests on

A program never names a platform parameter

Platform names live in the catalogue, not in the program. Roughly 95% of intents on a device declare no contract at all — an invented name would look right until runtime.

The machine is synchronous, the platform is not

A call queues an effect and returns an id; the answer arrives in a handler later. Which is why an intent cannot be an alarm clock — it dies with the program that made it.

Intents are gated by signature, the calendar is not

Without hos_system_app every intent call answers 202; without the ACL, 201. Calendar Kit is public, so schedules go through it, not through calendar intents.

The catalogue is data, not code

One row yields a compiler signature, a host call and a prompt paragraph. A new intent touches none of the three.
