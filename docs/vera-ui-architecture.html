VERA-L UI over ArkUI

How pure VERA-L functions produce native HarmonyOS interfaces through a five-stage pipeline with no direct ArkUI access.

Pipeline stages

1
Pure functions

A VERA-L program defines three things: init() returns the initial AppState, view(state) builds a UI tree from ui.* constructors, and one or more handlers like change(state, val) return a new state without mutation. These are ordinary functions — no framework hooks, no lifecycle, no side effects.

2
VM execution

The VBC2 VM calls view(state). Calls like ui.Column("spacious", [...]) dispatch to UiHostEnvironment, which doesn't render anything — it builds VeraObjectValue nodes with fields like {type: "button", action: "change", value: 1}. The result is a pure data tree of RuntimeValue objects.

3
decodeVeraUi()

Walks the RuntimeValue tree and flattens each node into a VeraUiNode — a typed struct with concrete fields (kind, style, text, action, eventValue, enabled, children). This is where the generic Map<string, RuntimeValue> becomes a shape ArkUI can consume.

4
@Builder renderNode()

In RunnerPage.ets, a single @Builder switches on node.kind and emits the corresponding ArkUI declarative component. Styles map to ArkUI properties — a closed set, not arbitrary CSS.

kindArkUI componentStyle applied via
"column"Column().padding, .alignItems
"row"Row().justifyContent
"text"Text(node.text).fontSize, .fontColor
"button"Button(node.text).onClick → handleAction
"card"Column().bg().radius().backgroundColor(variant)
"cell"Row()tap row style
"spacer"Blank()height
"image"Image(node.source).objectFit
"scroll"Scroll()nested children
5
Interaction loop

When the user taps a Button or Cell, ArkUI's onClick fires handleAction(node.action, node.eventValue). This calls the named handler via the VM, which returns a new AppState. The @State update triggers a reactive rebuild — the whole tree is replaced, no diffing.

@State → view() → decode → ArkUI → tap → handler() → new state

Pseudo-code

VERA-L program (user-authored)

import * as ui from "std/ui"

@jsonable
class AppState {
  count: int;
}

function init(): AppState {
  return {count: 0};
}

function change(state: AppState, amount: int): AppState {
  return {count: state.count + amount};
}

function view(state: AppState): ui.View {
  return ui.Column("spacious", [
    ui.Text("title", "Counter"),
    ui.Text("metric", ui.intToString(state.count)),
    ui.Row("spacious", [
      ui.Button("secondary", "-", "change", -1, true),
      ui.Button("primary",   "+", "change",  1, true)
    ])
  ]);
}

Host side (ArkTS, simplified)

// RunnerPage.ets — simplified pseudo-code

@State currentState: RuntimeValue = vm.execute("init", [])
@State nodes: VeraUiNode[] = decodeVeraUi(
  vm.execute("view", [currentState])
)

handleAction(action: string, value: number) {
  let intVal = new VeraIntValue(value)
  let newState = vm.execute(action, [currentState, intVal])
  currentState = newState
  nodes = decodeVeraUi(vm.execute("view", [newState]))
}

@Builder renderNode(node: VeraUiNode) {
  switch (node.kind) {
    case "column":
      Column() { ForEach(node.children, child => renderNode(child)) }
    case "text":
      Text(node.text).fontSize(styleToSize(node.style))
    case "button":
      Button(node.text)
        .onClick(() => handleAction(node.action, node.eventValue))
        .enabled(node.enabled)
  }
}

Design decisions

VERA-L never sees ArkUI

The ui.* functions in the VM just build value objects. All rendering is in one @Builder in RunnerPage — a single, mechanical mapping layer.

No diffing

Every state change rebuilds the full view tree. VERA-L programs stay under 80 nodes, so this is fast and avoids reconciliation complexity.

Actions are strings

ui.Button("primary", "+", "change", 1, true) stores the handler name "change" as a string. On tap, RunnerPage looks up and calls the VM function by name.

State is opaque

RunnerPage holds currentState as a RuntimeValue — it never inspects or modifies it. Only VERA-L handlers produce new state.

Styles are a closed set

Each component kind has a fixed set of allowed style names (Button: primary, secondary, success, danger). The @Builder maps these to ArkUI properties. No CSS, no arbitrary styling.
