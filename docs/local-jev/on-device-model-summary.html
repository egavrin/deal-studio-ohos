1. What the model is and what replaced what

Vera generates apps from a prompt in two model phases. The language model (cloud LLM) writes the program; the decision model (Jev) answers the structured selector questions the composer asks while assembling the program's screens — theme, widget, formula, step naming, and so on. One real generation asks roughly 15 of these per body, each with a handful of labelled options.

Historically every decision was a cloud call. The on-device work replaces the easy tier of those decisions with a local model, keeping the cloud for the rest:

The decisive detour on the way here: the attention score product (Q·KT) was believed to be a platform blocker — no transpose support in the HiAI op set, verified on two phones and two HiAI versions. It was not. It was two wire-format bugs in our own generator: the adj_x2 attribute must be boolean (an int-typed attribute is silently ignored, so the adjoint never applies and shape inference rejects the graph), and F16 weight Consts are rejected by the builder while F16 is fine after the LayerNorm gamma/beta stay F32. With both fixed, the full 22-layer model compiles and runs on the NPU with correct logits. The earlier "constraint map" is formally retracted in replacement-analysis.md §7.11.

The three backends share everything except the forward

The NPU integration point is infer_group inside the Rust engine: the graph replaces only the transformer forward. Tokenization, question batching, the embedding lookup, the marker scorer, and the serving calibration run host-side in Rust exactly as for the CPU path — the marker scorer consumes the NPU's hidden states in the same [B, S, 768] shape candle produces. This is why the correctness carries over: the calibration (laya-calibrate.py, fitted on the CPU outputs, n=109, 94.4% in-sample agreement) applies unchanged.

The serving graph

hiai-gen.py --batched 8 --seq 256 emits a fixed-shape graph from the validated numpy reference: 8 question slots padded to 256 tokens each, three inputs (raw embeddings [8·256, 768], the padding mask [8, 256, 256], the type embedding [8·256, 768]), and one output — the hidden states after the encoder, final norm, type add and head layers. One graph, one on-device compile (~2.1 s), any body; the padding mask (host-prepared from each question's real length) isolates slots so the padding cannot leak. The scorer stays host-side because the calibration is the product decision layer and per-body. Weights are F16 (accepted by the builder for the big projections), LayerNorm gamma/beta and the small tables F16-rejected and kept F32, identical Consts deduplicated — 278 MB total.

Fallback chain

Missing graph / build failure / question longer than 256 → candle CPU → below-confidence or cloud-tier → cloud batch. Every level degrades independently; the E2E pipeline never hard-depends on the NPU.

The honest headline: the NPU's raw forward is 4× faster, but the pipeline is not yet faster — 94.8 s vs 86.4 s for the Jev phase. The measured gap comes from fixed-shape padding waste (every batch pays the full 8×256 slots while real questions average ~150 tokens), first-run compile/init, and the cloud fallback round trip, which dominates both hybrid rows equally. And every hybrid route is ~8× slower than pure cloud on wall clock; the hybrid's value is availability (no network, no tail), not speed.

3.5 Model-level facts for feasibility

  • Compute per question: ~20.5 GFLOP at ~110 tokens (Laya encoder, 22×768). This is fixed by architecture — the rejected openJev-151M shares the same encoder, so a smaller parameter count was not a speed lever (the parameter difference is embedding lookups, no FLOPs).
  • Speed levers already tried and measured: question batch 4→8 kept (+5%); max_len 512 halving rejected (+3%, identical answers); threading already parallel; state-sharing (prefix KV) rejected on quality (27.7% argmax flips, ~86% agreement ceiling).
  • Calibration is the serving gate: fitted in-sample (n=109); the per-type refit at scale is the documented follow-up.

4. Improvement proposals — and what came of them

Three of the levers below were implemented on 2026-11-27 (commits 78459fe, ebe7f73); their measured results are marked inline. The honest headline: all three work as designed, and the E2E time stayed flat — the bucketed local phase measured ~79–81 s against the 73–84 s S=256 baseline, so the expected ~14 s padding saving is within noise, not demonstrated. The per-batch NPU cost may not be shape-proportional at these sizes; resolving that needs per-batch trace timing (still to do).

Model / serving tuning

  1. Bucketed graph shapes implemented, flat result — the registry now takes multiple (path, batch, seq) graphs; infer_group picks the smallest bucket that fits the group and compiles it lazily (persisted). S=192 B=8 replaced S=256 B=8 in the test build (S=384 B=4 was generated and validated but dropped on disk constraints). Correct answers, flat E2E time.
  2. Parallel hard tier implemented, verified — the hard-tier cloud batch now runs concurrently with the local forward; the Jev phase is max(cloud, local + fallback) instead of the sum. Verified in a live generation.
  3. Dynamic-shape graphs — the HIAI_MR_DynamicShapeConfig API exists in libhiai (enable + 1..10 cached shapes); untested. If it works, one compile serves all lengths and the padding waste disappears entirely. Now the highest-value untried lever.
  4. Warm-process amortization — the compile + engine construction are once per process; a second generation in a warm process skips them. Still unmeasured (the result screen's New navigation resists programmatic driving).
  5. Per-type calibration refit at scale — the current fit is global and in-sample; a recorded set at scale would sharpen min_confidence per question type and lift the served fraction.
  6. Graph quantization — the graph stores F16 weights (F16 rejected only for LN gamma/beta); int8 weight quantization of the projections would halve the graph again if the builder accepts it, and is the shipping path for the 547 MB HAP problem.
  7. openJev-151M as the packaging option — same FLOPs, 3× smaller Q4 bundle, genuine held-out calibration; a quality/packaging choice, not a speed choice.

OS capability

  • Model persistence implemented, verified — SaveToFile/RestoreFromFile wired into the Rust forward; the compiled graph is cached beside the graph file and cold starts skip the compile (~2.1 s saved; the 3.7–6.5 s init remains either way).
  • Per-backend NNRT access — the MindSpore NNRT service is deployed but SELinux-gated for debug-profile apps on retail devices; an OS-level permission for signed apps would open the second NPU door and give a vendor-independent fallback.
  • Foreground scheduling — the NPU forward runs in the app's process with ordinary priority; a QoS class for on-device inference during generation would tighten the first-batch latency.

Hardware (CPU and NPU)

  • CPU ceiling — candle runs ~4 GFLOPS effective on the Kirin CPU (5.3/8 cores); a llama.cpp-grade Q4 kernel rewrite is the only remaining CPU lever, est. 2–3×.
  • NPU generation — the Kirin 9030 executes the full attention stack once the attr bug is fixed; older HiAI builds (106/107 on the other phones) need the re-run to confirm the same. NPU FLOPS at B=8/S=256 imply ~17–20 GFLOPS effective — an order over CPU, with the fixed-shape overhead, not compute, as today's limiter.
  • DSP/other accelerators — HiAI exposes AIPP + quantized-tuning options at build time; exploring INT8 execution for the encoder is the natural next experiment.

5. The feasibility record

questionanswer
Can the full decision model run on the NPU?Yes — 22 layers, correct logits (Δ 0.002), on Kirin 9030. The "attention transpose blocker" was our attr-encoding bug, not silicon.
Is the NPU path integrated end to end?Yes — a real hybrid generation served 5–7/15 decisions on the NPU with cloud fallback, in the shipped pipeline.
Does it make the pipeline faster today?No — ~86–95 s vs 86.4 s (CPU) Jev phase, flat across the S=256, bucketed S=192, persisted and parallel-routing variants. The 4× forward win is eaten by the fixed-shape overhead, the engine construction and the cloud fallback; padding reduction (S=192 buckets) did not move the total within measurement noise.
Does it change answer quality?No — within candle's own run-to-run variance; the NPU is closer to the spec than candle is.
Why run local at all?Availability: offline generation, no network tail, no per-decision cloud cost. Speed was the hoped-for bonus; it is not yet realized.
